# 07. 문제 해결과 안전 수칙

Git 오류가 나면 강제 명령부터 쓰지 마세요. 대부분은 **현재 폴더, 현재 브랜치, 파일 상태, 원격 주소**를 확인하면 원인을 찾을 수 있습니다.

## 1. 공통 진단 순서

아래 명령은 대부분 읽기 전용이라 안전합니다.

```powershell
Get-Location
git rev-parse --show-toplevel
git status
git branch -vv
git remote -v
git log --oneline --graph --decorate --all -15
```

차례대로 다음을 묻습니다.

1. 올바른 프로젝트 폴더에 있는가?
2. Git 저장소 안에 있는가?
3. 현재 브랜치가 맞는가?
4. 커밋하지 않은 변경이나 충돌이 있는가?
5. 로컬 브랜치와 원격 브랜치가 어떻게 연결되어 있는가?
6. `origin` 주소가 내 저장소 주소와 일치하는가?

오류 메시지는 지우지 말고 첫 줄부터 읽습니다. 질문할 때는 비밀번호·토큰을 제외하고 실행한 명령, 전체 오류, 위 진단 결과를 함께 전달하면 해결이 빨라집니다.

## 2. `git`을 명령으로 인식하지 못함

대표 메시지:

```text
git : 'git' 용어가 cmdlet, 함수, 스크립트 파일 또는 실행할 수 있는 프로그램 이름으로 인식되지 않습니다.
```

확인:

```powershell
Get-Command git -ErrorAction SilentlyContinue
```

해결 순서:

1. Git이 설치되었는지 확인합니다.
2. 설치 직후라면 모든 PowerShell 창을 닫고 새로 엽니다.
3. 다시 `git --version`을 실행합니다.
4. 계속 실패하면 Git for Windows를 다시 설치하면서 명령줄에서 Git을 사용할 수 있는 기본 PATH 옵션을 유지합니다.

설치: [Git for Windows 공식 페이지](https://git-scm.com/install/windows)

## 3. `not a git repository`

대표 메시지:

```text
fatal: not a git repository (or any of the parent directories): .git
```

현재 폴더가 저장소가 아니거나 엉뚱한 폴더에 있습니다.

```powershell
Get-Location
Get-ChildItem -Force
```

- 기존 프로젝트라면 `.git`이 있는 프로젝트 폴더로 `Set-Location` 합니다.
- 새 프로젝트이고 정말 이 폴더에서 Git을 시작하려는 경우에만 `git init -b main`을 실행합니다.
- 오류를 없애기 위해 아무 폴더에서나 `git init`을 실행하지 마세요. 저장소가 중첩될 수 있습니다.

## 4. `Author identity unknown`

커밋 작성자 이름이나 이메일이 설정되지 않은 상태입니다.

```powershell
git config --global user.name "내 이름"
git config --global user.email "GitHub에 등록한 이메일"
git config --global --get user.name
git config --global --get user.email
```

회사 저장소에서만 다른 이메일을 쓰려면 해당 저장소 폴더에서 `--global` 대신 `--local`을 사용합니다.

## 5. 인증 실패 또는 계속 로그인 요청

먼저 원격 주소를 확인합니다.

```powershell
git remote -v
```

HTTPS 주소가 실제 저장소와 다르면 수정합니다.

```powershell
git remote set-url origin 'https://github.com/실제-사용자명/실제-저장소명.git'
```

확인할 사항:

- 브라우저에 올바른 GitHub 계정으로 로그인했는가?
- 그 계정에 해당 저장소의 접근 권한이 있는가?
- 이메일 인증과 필요한 2FA 절차를 완료했는가?
- GitHub 계정 비밀번호를 Git 명령줄에 넣으려 한 것은 아닌가?

Git Credential Manager의 브라우저 승인을 다시 진행하거나, 선택 사항으로 GitHub CLI에서 `gh auth login`을 사용할 수 있습니다. 토큰을 만들었다면 화면 공유, 소스 파일, 커밋 메시지에 노출하지 마세요.

공식 참고: [GitHub 인증 방식 안내](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/about-authentication-to-github)

## 6. `remote origin already exists`

이미 `origin`이 등록된 상태에서 다시 추가하려 하면 발생합니다.

```powershell
git remote -v
```

주소가 맞으면 아무것도 할 필요가 없습니다. 주소가 틀렸다면 `add`가 아니라 `set-url`을 사용합니다.

```powershell
git remote set-url origin 'https://github.com/사용자명/저장소명.git'
git remote -v
```

## 7. `src refspec main does not match any`

주요 원인은 아직 커밋이 없거나 현재 브랜치 이름이 `main`이 아닌 경우입니다.

```powershell
git status
git branch --show-current
git log --oneline
```

커밋이 없다면 파일을 만든 뒤 첫 커밋을 생성합니다.

```powershell
git add README.md
git commit -m "Add project README"
git push -u origin main
```

브랜치 이름이 다르다면 실제 브랜치 이름으로 push하거나, 팀 규칙을 확인한 뒤 이름을 정리합니다.

## 8. push가 `non-fast-forward`로 거절됨

원격 브랜치에 로컬에 없는 커밋이 있다는 뜻입니다. 다른 사람이 push했거나 GitHub 웹에서 파일을 수정했을 수 있습니다.

먼저 작업 상태를 확인합니다.

```powershell
git status
git fetch origin
git log --oneline --graph --decorate --all -15
```

작업 폴더가 깨끗하고 단순히 뒤처진 경우:

```powershell
git pull --ff-only
git push
```

`--ff-only`도 중단되면 로컬과 원격이 각각 진행된 상태입니다. 팀 작업이라면 이력을 임의로 덮어쓰지 말고 merge 또는 rebase 정책을 확인합니다. 초보자는 `git push --force`로 해결하려 하지 마세요.

### GitHub 저장소를 만들 때 README를 함께 생성한 경우

로컬과 GitHub에 서로 다른 첫 커밋이 생겼을 수 있습니다. 아직 중요한 기록이 없는 개인 연습이라면 가장 단순한 방법은 GitHub 저장소를 **비어 있는 상태로 다시 만들고** 연결하는 것입니다.

원격의 README도 보존해야 한다면 새 폴더에 GitHub 저장소를 clone하고, 그 폴더로 로컬 파일을 복사한 뒤 정상적인 `add → commit → push` 흐름을 사용하는 편이 초보자에게 안전합니다. 중요한 저장소에서는 삭제나 강제 push 전에 경험자에게 확인하세요.

## 9. 브랜치를 바꿀 수 없음

대표 원인:

- 저장하지 않은 수정이 대상 브랜치의 파일과 충돌함
- merge 또는 rebase가 진행 중임
- 입력한 브랜치가 존재하지 않음

진단:

```powershell
git status
git branch --all
```

현재 변경이 완성되었다면 커밋합니다. 잠시 보관하려면 stash합니다.

```powershell
git stash push -m "WIP before switching branch"
git switch main
```

나중에 원래 브랜치로 돌아와 복원합니다.

```powershell
git switch feature/login
git stash pop
```

## 10. merge conflict

충돌은 같은 부분을 서로 다르게 고쳐 Git이 자동으로 최종 내용을 정하지 못한 상태입니다.

```powershell
git status
```

해결 순서:

1. `both modified`로 표시된 파일을 엽니다.
2. `<<<<<<<`, `=======`, `>>>>>>>` 사이의 양쪽 내용을 읽습니다.
3. 유지할 최종 내용으로 직접 수정합니다.
4. 충돌 표시가 모두 제거되었는지 검색합니다.
5. 해결한 파일을 add하고 commit합니다.

```powershell
git add message.txt
git status
git commit -m "Resolve merge conflict in message.txt"
```

병합을 포기하고 시작 전으로 돌아가려면 병합 커밋 전에 실행합니다.

```powershell
git merge --abort
```

## 11. `LF will be replaced by CRLF` 경고

Windows와 Linux/macOS의 줄바꿈 방식 차이 때문에 나올 수 있는 경고이며, 보통 명령 실패는 아닙니다.

- 팀에 `.gitattributes` 규칙이 있으면 그 규칙을 따릅니다.
- 경고만 보고 파일 전체를 다시 저장하거나 전역 설정을 무작정 바꾸지 않습니다.
- 실제 변경이 줄바꿈뿐인지 `git diff`로 확인합니다.

팀 프로젝트에서는 `.gitattributes`로 저장소 차원의 줄바꿈 정책을 정하는 것이 일관적입니다.

## 12. Detached HEAD

특정 과거 커밋을 직접 체크아웃하면 브랜치가 아닌 커밋에 머무는 detached HEAD 상태가 될 수 있습니다.

```powershell
git status
git branch --show-current
```

구경만 했다면 기존 브랜치로 돌아갑니다.

```powershell
git switch main
```

그 상태에서 만든 커밋을 보존하고 싶다면 이동하기 전에 새 브랜치를 만듭니다.

```powershell
git switch -c recovery/keep-work
```

## 13. `.gitignore`에 썼는데 파일이 계속 보임

`.gitignore`는 아직 추적하지 않는 파일에 적용됩니다. 이미 커밋한 파일은 계속 추적됩니다.

먼저 정말 원격에서 제거해도 되는 파일인지 확인한 뒤, 파일은 로컬에 남기고 Git 추적만 해제할 수 있습니다.

```powershell
git rm --cached '.env'
git add .gitignore
git commit -m "Stop tracking local configuration"
```

민감 정보가 이미 커밋되었다면 이 방법만으로 과거 이력에서 사라지지 않습니다. 다음 절차를 따릅니다.

## 14. 비밀번호나 API 키를 커밋함

가장 먼저 해야 할 일은 Git 명령이 아니라 **해당 비밀값을 폐기·교체하는 것**입니다.

1. 서비스 제공자 화면에서 노출된 비밀번호, 토큰, API 키를 즉시 취소하거나 회전합니다.
2. 저장소 관리자와 팀에 알립니다.
3. 새 비밀값은 환경 변수나 승인된 비밀 관리 도구로 옮깁니다.
4. `.gitignore`에 비밀 파일 패턴을 추가합니다.
5. 과거 Git 이력 제거는 저장소 전체에 영향을 줄 수 있으므로 공식 절차와 팀 협의를 따릅니다.

파일을 지우고 새 커밋을 만들거나 저장소를 Private로 바꾸는 것만으로 이미 노출된 비밀이 안전해지지는 않습니다.

공식 참고: [저장소에서 민감한 데이터 제거](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)

## 15. 안전 수칙

### 커밋 전에 항상 확인

```powershell
git status
git diff
git diff --staged
```

다음을 점검합니다.

- 의도하지 않은 파일이 stage되지 않았는가?
- 비밀번호, API 키, 개인 정보가 들어 있지 않은가?
- 대용량 데이터, 빌드 결과, 가상환경 폴더가 포함되지 않았는가?
- 디버그 코드나 임시 출력이 남지 않았는가?

### 뜻을 알기 전에는 피하기

```text
git reset --hard       # 커밋하지 않은 변경을 잃을 수 있음
git clean -fd          # 추적되지 않은 파일·폴더를 삭제할 수 있음
git push --force       # 원격 공유 이력을 덮어쓸 수 있음
git branch -D          # 병합되지 않은 브랜치를 강제로 삭제
```

인터넷에서 본 명령은 현재 상황과 다를 수 있습니다. 먼저 백업 가능한지, 어느 저장소와 브랜치에 영향을 주는지 확인합니다.

## 16. 도움을 요청할 때 준비할 정보

다음 결과를 텍스트로 준비하면 좋습니다.

```powershell
git --version
Get-Location
git status
git branch -vv
git remote -v
git log --oneline --graph --decorate --all -15
```

단, 원격 URL에 비밀 토큰이 포함되어 있다면 반드시 가리고 공유합니다. 비밀번호, 토큰, 개인 키, `.env` 내용은 절대 첨부하지 않습니다.
