# 4차시. 브랜치 분기 심화 실습

## 수업 개요

- 권장 시간: 80~100분
- 선수 학습: 브랜치 전환, commit·push, PR 또는 로컬 merge
- 완료 결과: 형제 브랜치, 연쇄 브랜치, 역할 기반 브랜치의 시작점과 병합 방향을 구분합니다.
- 선택 확장: 한 PC에서 여러 작업 폴더를 사용하는 `git worktree`를 시연합니다.

## 학습 목표

1. 브랜치는 **현재 커밋 또는 지정한 시작점**에서 만들어진다는 사실을 확인합니다.
2. 같은 `main`에서 만든 형제 브랜치와 다른 작업 브랜치에서 만든 연쇄 브랜치를 구분합니다.
3. 로컬 브랜치와 `origin/...` 원격 추적 브랜치를 구분합니다.
4. `main → develop → feature` 같은 역할 기반 흐름의 장단점을 설명합니다.

## 0. 시작 상태와 main 기둥 준비

```powershell
# 실습 저장소로 이동
$classRoot = Join-Path ([Environment]::GetFolderPath('MyDocuments')) 'git-class-practice'
$demoRepo = Join-Path $classRoot 'git-class-demo'
Set-Location $demoRepo

# 최신의 깨끗한 main 확인
git status
git switch main
git pull --ff-only
```

관찰용 기둥 파일이 없다면 만듭니다.

```powershell
# main에 모든 분기의 공통 기준 파일 생성
@'
main 기둥에서 시작합니다.
'@ | Set-Content -Encoding utf8 trunk.txt

git add trunk.txt
git diff --staged
git commit -m "Add branch structure trunk"
git push origin main
```

이미 `trunk.txt`가 커밋된 재수업 환경이라면 이 단계는 생략합니다.

## 1. 구조 A: 같은 main에서 나온 형제 브랜치

첫 번째 브랜치를 `main`에서 만듭니다.

```powershell
# main을 시작점으로 첫 번째 형제 브랜치 생성
git switch main
git switch -c practice/sibling-a

# 첫 번째 브랜치 전용 파일과 커밋
'첫 번째 형제 브랜치의 파일' | Set-Content -Encoding utf8 sibling-a.txt
git add sibling-a.txt
git commit -m "Add sibling A file"
git push -u origin practice/sibling-a
```

두 번째 브랜치도 반드시 `main`으로 돌아간 뒤 만듭니다.

```powershell
# 첫 번째 브랜치가 아니라 main에서 새로 분기
git switch main
git switch -c practice/sibling-b

# 두 번째 브랜치 전용 파일과 커밋
'두 번째 형제 브랜치의 파일' | Set-Content -Encoding utf8 sibling-b.txt
git add sibling-b.txt
git commit -m "Add sibling B file"
git push -u origin practice/sibling-b
```

그래프를 확인합니다.

```powershell
git log --oneline --graph --decorate --all -15
```

개념 그림:

```text
             A1  practice/sibling-a
            /
main ------M
            \
             B1  practice/sibling-b
```

관찰 질문:

- `sibling-a`에 `sibling-b.txt`가 있는가?
- `sibling-b`에 `sibling-a.txt`가 있는가?
- 두 브랜치가 공유하는 마지막 커밋은 무엇인가?

형제 브랜치는 서로의 작업을 자동으로 포함하지 않습니다. 각각 `main`에 독립 PR을 만들기 좋습니다.

## 2. 구조 B: 작업 브랜치에서 다시 나온 연쇄 브랜치

이번에는 `practice/sibling-a`에서 잔가지 브랜치를 만듭니다.

```powershell
# 첫 번째 작업 브랜치로 이동
git switch practice/sibling-a

# sibling-a의 커밋을 시작점으로 세부 브랜치 생성
git switch -c practice/stacked-detail

# 잔가지 전용 파일 추가
'sibling-a 위에 쌓인 세부 작업' | Set-Content -Encoding utf8 stacked-detail.txt
git add stacked-detail.txt
git commit -m "Add stacked detail file"
git push -u origin practice/stacked-detail
```

```powershell
# main과 비교했을 때 포함되는 커밋 확인
git log --oneline main..practice/stacked-detail

# sibling-a와 비교했을 때 새로 추가된 커밋 확인
git log --oneline practice/sibling-a..practice/stacked-detail
```

개념 그림:

```text
main ------M
            \
             A1  practice/sibling-a
               \
                D1  practice/stacked-detail
```

핵심:

- `stacked-detail`에는 `A1`과 `D1`이 모두 포함됩니다.
- `stacked-detail → main` PR을 바로 만들면 `sibling-a`의 변경까지 함께 보일 수 있습니다.
- 세부 변경만 먼저 검토하려면 PR 방향을 `base: practice/sibling-a`, `compare: practice/stacked-detail`로 잡습니다.
- `sibling-a`가 main에 먼저 병합된 뒤 세부 PR의 base를 main으로 바꾸는 흐름을 사용할 수 있습니다.

연쇄 브랜치는 큰 작업을 순차 리뷰할 때 유용하지만, 시작점을 모르면 PR에 예상보다 많은 파일이 포함되어 초보자가 혼란스러울 수 있습니다.

## 3. 구조 C: 역할 기반 main·develop·feature

작업 규모가 커지면 브랜치 이름에 역할을 부여할 수 있습니다.

```text
main       : 배포·제출 가능한 안정 상태
develop    : 다음 배포를 준비하는 통합 상태
feature/*  : 기능 하나를 구현하는 짧은 작업 브랜치
```

연습용 명령:

```powershell
# 최신 main에서 통합 브랜치 생성
git switch main
git pull --ff-only
git switch -c develop
git push -u origin develop

# develop에서 기능 브랜치 생성
git switch -c feature/student-search
'학생 검색 기능 실습 파일' | Set-Content -Encoding utf8 student-search.txt
git add student-search.txt
git commit -m "Add student search practice"
git push -u origin feature/student-search
```

협업 방향:

```text
feature/student-search
  → PR과 리뷰
  → develop
  → 여러 기능 통합·검증
  → 배포 준비 PR
  → main
```

모든 팀에 `develop`이 필요한 것은 아닙니다. 소규모 팀과 빠른 배포 프로젝트는 최신 `main`에서 짧은 feature 브랜치를 만들고 바로 PR하는 GitHub Flow가 더 단순할 수 있습니다.

강사 질문:

> “브랜치가 많을수록 무조건 더 전문적인가요?”

기대 답변: 아닙니다. 실제 리뷰·배포 흐름에 필요한 최소 구조가 좋습니다.

## 4. 로컬 브랜치와 원격 브랜치 구분

```powershell
# 로컬 브랜치 목록
git branch

# 원격 추적 브랜치 목록
git branch --remotes

# 로컬과 원격을 모두 표시
git branch --all

# upstream과 ahead/behind 관계 확인
git branch -vv
```

표시를 다음처럼 읽습니다.

```text
develop                     → 로컬에서 이동·커밋할 수 있는 브랜치
origin/develop              → 마지막 fetch 시점에 알고 있는 원격 develop 상태
origin/feature/student-search → 원격 feature 브랜치의 로컬 추적 참조
```

`origin/develop`은 GitHub 서버를 실시간으로 들여다보는 화면이 아닙니다. 최신 원격 참조는 `git fetch origin` 후 확인합니다.

## 5. 세 구조 비교

| 구조 | 시작점 | 장점 | 주의 |
|---|---|---|---|
| 형제 브랜치 | 각각 최신 `main` | PR 범위가 독립적이고 단순 | 공통 선행 작업이 필요하면 중복될 수 있음 |
| 연쇄 브랜치 | 다른 작업 브랜치 | 큰 작업을 순서대로 나눠 리뷰 | base 선택을 잘못하면 선행 변경까지 PR에 포함 |
| 역할 기반 | `main → develop → feature` | 통합·배포 단계를 명확히 분리 | 작은 팀에는 불필요하게 복잡할 수 있음 |

학생에게 “새 브랜치를 어디에서 만들었는가?”를 항상 답하게 합니다.

## 6. 선택 시연: 한 PC에서 여러 Worktree 사용

일반적으로 한 Git 저장소의 작업 폴더는 한 번에 한 브랜치를 보여 줍니다. `git worktree`를 사용하면 같은 저장소의 브랜치를 별도 폴더에 체크아웃해 동시에 열 수 있습니다.

```powershell
# 현재 저장소와 두 번째 작업 폴더의 절대 경로 준비
$demoRepo = Join-Path $classRoot 'git-class-demo'
$docsWorktree = Join-Path $classRoot 'git-class-demo-docs'

# main에서 새 브랜치를 만들며 두 번째 worktree 추가
git -C $demoRepo worktree add $docsWorktree -b practice/docs-worktree main

# 두 폴더가 서로 다른 브랜치를 사용하는지 확인
git -C $demoRepo branch --show-current
git -C $docsWorktree branch --show-current
git -C $demoRepo worktree list
```

두 번째 폴더에서만 파일을 만들고 커밋합니다.

```powershell
# 별도 worktree에 문서 파일 생성
'별도 worktree에서 작성한 문서' | Set-Content -Encoding utf8 (Join-Path $docsWorktree 'worktree-note.md')

# 별도 worktree의 브랜치에만 커밋
git -C $docsWorktree add worktree-note.md
git -C $docsWorktree commit -m "Add worktree practice note"

# 두 worktree의 상태와 브랜치 확인
git -C $demoRepo status --short --branch
git -C $docsWorktree status --short --branch
```

같은 브랜치는 동시에 두 worktree에 체크아웃할 수 없습니다. `git branch -vv`에서 다른 worktree에 체크아웃된 브랜치 앞에 `+`가 표시될 수 있습니다.

### 선택 시연 정리

다음 명령은 **수업 전용 worktree 경로가 맞고 두 worktree가 모두 깨끗한지 확인한 뒤에만** 실행합니다.

```powershell
# 원래 worktree의 main에 실습 브랜치 병합
git -C $demoRepo switch main
git -C $demoRepo merge practice/docs-worktree
git -C $demoRepo push origin main

# 별도 worktree가 깨끗한지 확인
git -C $docsWorktree status

# 정확히 지정한 수업용 두 번째 작업 폴더 연결 제거
git -C $demoRepo worktree remove $docsWorktree

# main에 병합된 로컬 실습 브랜치 삭제
git -C $demoRepo branch -d practice/docs-worktree
```

`worktree remove`는 해당 worktree 작업 폴더를 제거하므로 다른 프로젝트 경로를 넣지 않도록 주의합니다. 커밋하지 않은 변경이 있으면 먼저 보존합니다.
