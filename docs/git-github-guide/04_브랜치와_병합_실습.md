# 04. 브랜치와 병합 실습

이 장에서는 작업 브랜치를 직접 만들고, `main`과 파일 상태가 달라지는 것을 관찰한 뒤 fast-forward 병합과 충돌이 있는 3-way 병합을 차례대로 연습합니다.

## 브랜치 실습의 핵심 그림

```text
처음
A---B  main

feature 브랜치에서 작업
A---B  main
     \
      C---D  feature/greeting(브런치명)

main에 병합
A---B---C---D  main
              feature/greeting(브런치명)
```

브랜치는 폴더 복사본이 아니라 커밋을 가리키는 이름표입니다. `git switch`로 브랜치를 바꾸면 작업 폴더의 파일도 그 브랜치가 가리키는 커밋 상태로 바뀝니다.

## 0. 실습 저장소 준비

[이전 실습](./03_로컬에서_GitHub까지_첫_실습.md)의 원본 `hello-git` 폴더에서 시작합니다. 새 PowerShell을 열었다면 다음과 같이 이동합니다.

```powershell
$practiceRoot = Join-Path ([Environment]::GetFolderPath('MyDocuments')) 'git-practice'
Set-Location (Join-Path $practiceRoot 'hello-git')
```

항상 깨끗한 최신 `main`에서 시작합니다.

```powershell
git status
git switch main
git pull --ff-only
```

`working tree clean`을 확인한 뒤 진행하세요. 수정 중인 파일이 있다면 먼저 커밋하거나 stash해야 합니다.

## 1. 첫 작업 브랜치 만들기

```powershell
git switch -c feature/greeting
git branch
```

- `switch -c`: 새 브랜치를 만들고 즉시 이동합니다.
- `feature/greeting`: 기능 목적을 드러내는 브랜치 이름입니다.
- `git branch`의 `*`: 현재 브랜치를 표시합니다.

현재 브랜치 이름만 확인하려면 다음 명령도 쓸 수 있습니다.

```powershell
git branch --show-current
```

## 2. 브랜치에서 작업하고 커밋하기

새 파일을 만듭니다.

```powershell
@'
안녕하세요!
이 파일은 feature/greeting 브랜치에서 만들었습니다.
'@ | Set-Content -Encoding utf8 greeting.txt
```

상태와 차이를 확인한 뒤 커밋합니다.

```powershell
git status
git add greeting.txt
git diff --staged
git commit -m "Add greeting message"
git log --oneline --decorate -3
```

`feature/greeting`이 새 커밋을 가리키고 있습니다.

## 3. main으로 이동해 차이 관찰하기

```powershell
git switch main
Test-Path greeting.txt
git log --oneline --decorate -3
```

`Test-Path`가 `False`라면 정상입니다. `greeting.txt`는 feature 브랜치에서 만든 커밋에만 있기 때문입니다. 파일이 사라진 것이 아니라 브랜치를 바꾸면서 작업 폴더가 `main`의 상태로 바뀐 것입니다.

다시 feature 브랜치로 가면 파일이 나타납니다.

```powershell
git switch feature/greeting
Test-Path greeting.txt
Get-Content greeting.txt
```

## 4. feature를 main에 fast-forward 병합하기

병합할 때는 먼저 **변경을 받을 브랜치**로 이동합니다. 여기서는 `main`이 결과를 받아야 합니다.

```powershell
git switch main
git merge feature/greeting
```

출력에 `Fast-forward`가 보일 가능성이 큽니다. feature가 갈라진 뒤 `main`에 다른 커밋이 없으므로 `main` 포인터만 feature의 끝으로 이동할 수 있기 때문입니다.

확인하고 GitHub에도 보냅니다.

```powershell
git log --oneline --graph --decorate --all -8
Get-Content greeting.txt
git push
```

병합이 끝난 로컬 브랜치를 삭제합니다.

```powershell
git branch -d feature/greeting
git branch
```

`-d`는 병합되지 않은 작업을 실수로 지우지 않도록 거부하는 안전한 삭제 옵션입니다. `-D`는 강제 삭제이므로 초보 실습에서는 사용하지 않습니다.

## 5. 3-way merge와 충돌 준비하기

이번에는 두 브랜치가 같은 파일의 같은 줄을 서로 다르게 수정하도록 만들어 충돌을 관찰합니다.

먼저 `main`에 기준 파일을 만들고 커밋합니다.

```powershell
"공통 시작 문장" | Set-Content -Encoding utf8 message.txt
git add message.txt
git commit -m "Add base message"
```

충돌 연습 브랜치를 만들고 문장을 바꿉니다.

```powershell
git switch -c practice/merge-conflict
"브랜치에서 바꾼 문장" | Set-Content -Encoding utf8 message.txt
git add message.txt
git commit -m "Edit message on practice branch"
```

이제 `main`으로 돌아가 같은 줄을 다른 내용으로 바꿉니다.

```powershell
git switch main
"main에서 바꾼 문장" | Set-Content -Encoding utf8 message.txt
git add message.txt
git commit -m "Edit message on main"
```

두 브랜치가 서로 다른 커밋으로 진행된 모습부터 확인합니다.

```powershell
git log --oneline --graph --decorate --all -10
```

## 6. 일부러 충돌 발생시키기

현재 `main`에서 연습 브랜치를 병합합니다.

```powershell
git merge practice/merge-conflict
```

이 명령은 `CONFLICT`를 표시하고 멈추는 것이 정상입니다. 상태와 파일을 확인합니다.

```powershell
git status
Get-Content message.txt
```

파일에는 다음과 비슷한 충돌 표시가 들어 있습니다.

```text
 <<<<<<< HEAD
main에서 바꾼 문장
 =======
브랜치에서 바꾼 문장
 >>>>>>> practice/merge-conflict
```

- `<<<<<<< HEAD`부터 `=======` 전까지: 현재 브랜치인 `main`의 내용
- `=======`부터 `>>>>>>> ...` 전까지: 병합하려는 브랜치의 내용

이 표시는 최종 문서에 남길 내용이 아닙니다. 사람이 두 의도를 이해하고 최종 내용을 직접 작성해야 합니다.

## 7. 충돌 해결하고 병합 완료하기

두 의견을 함께 반영한 최종 내용으로 파일을 덮어씁니다.

```powershell
@'
main과 연습 브랜치의 내용을 검토해 하나로 합쳤습니다.
'@ | Set-Content -Encoding utf8 message.txt
```

충돌 표시가 사라졌는지 확인하고, 해결한 파일을 add한 뒤 병합 커밋을 완료합니다.

```powershell
Get-Content message.txt
git add message.txt
git status
git commit -m "Resolve message merge conflict"
```

그래프로 확인합니다.

```powershell
git log --oneline --graph --decorate --all -12
```

두 갈래가 하나의 병합 커밋에서 다시 만나는 모습이 보이면 성공입니다.

```powershell
git push
git branch -d practice/merge-conflict
```

## 8. 해결을 포기하고 병합 전으로 돌아가려면

충돌 해결 중 아직 어떤 파일도 커밋하지 않았고 병합 자체를 취소하려면 다음 명령을 사용합니다.

```powershell
git merge --abort
```

이 명령은 진행 중인 merge를 시작 전 상태로 되돌립니다. 이미 충돌 해결 커밋까지 만들었다면 실행 대상이 아닙니다.

## 9. 브랜치 명령 정리

| 목적 | PowerShell에서 실행할 Git 명령 |
|---|---|
| 현재 브랜치 확인 | `git branch --show-current` |
| 로컬 브랜치 목록 | `git branch` |
| 원격 포함 전체 목록 | `git branch --all` |
| 새 브랜치 생성과 이동 | `git switch -c feature/name` |
| 기존 브랜치로 이동 | `git switch main` |
| 직전 브랜치로 이동 | `git switch -` |
| 현재 브랜치에 다른 브랜치 병합 | `git merge feature/name` |
| 병합된 로컬 브랜치 삭제 | `git branch -d feature/name` |
| 원격 브랜치 삭제 | `git push origin --delete feature/name` |
| 커밋 그래프 보기 | `git log --oneline --graph --decorate --all` |

## 10. 좋은 브랜치 습관

- 새 브랜치는 최신 `main`에서 만듭니다.
- 브랜치 하나에는 기능·수정 하나만 담습니다.
- 이름만 보고 목적을 알 수 있게 `feature/login`, `fix/cart-total`, `docs/git-guide`처럼 짓습니다.
- 작업 중에는 작고 의미 있는 단위로 커밋합니다.
- 병합한 브랜치는 삭제해 목록을 단순하게 유지합니다.
- 여러 사람이 쓰는 저장소에서는 `main`에 직접 push하기보다 Pull Request를 사용합니다.

## 11. 완료 점검

- [ ] `git switch -c`로 브랜치를 만들고 이동했다.
- [ ] 브랜치마다 작업 폴더의 파일 상태가 달라지는 것을 확인했다.
- [ ] `main`으로 이동한 뒤 feature 브랜치를 병합했다.
- [ ] fast-forward가 무엇인지 설명할 수 있다.
- [ ] 같은 줄을 다르게 수정해 충돌을 발생시켰다.
- [ ] 충돌 표시를 제거하고 `add → commit`으로 해결했다.
- [ ] merge는 insert/update 두 종류라는 뜻이 아님을 설명할 수 있다.
